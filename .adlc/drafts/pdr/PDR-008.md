## PDR-008: Google Tasks OAuth2 Authentication

### Status

**Proposed**

### Date

2026-08-24

### Owner

User/AI collaboration

### Category

Feature

### Feature-Area

core

### Context
**Problem/Opportunity:**
Google Tasks integration requires OAuth2 authentication to access user task data. The app needs to obtain and refresh OAuth2 tokens securely within the Electron desktop environment.

**Market Forces:**
- Google Tasks API requires OAuth2 for user data access
- Electron apps have specific security considerations for token storage
- User expects seamless authentication without exposing credentials

### Decision
**Decision Statement:**
Implement Google Tasks OAuth2 using the authorization code flow with PKCE, storing refresh tokens in OS keychain via Electron's safeStorage API.

**Rationale:**
Authorization code with PKCE is Google's recommended flow for desktop apps. OS keychain storage aligns with PDR-002's BYOK key storage pattern, maintaining consistency across credential handling.

### Consequences
#### Positive
- Follows Google's recommended desktop OAuth2 pattern
- Consistent with existing key storage approach (PDR-002)
- PKCE provides protection against authorization code interception

#### Negative
- Requires Google Cloud Console project setup with redirect URI configuration
- Token refresh adds complexity to sync lifecycle

#### Risks
- Google OAuth consent screen review delays → start with testing mode, request broad scopes early
- Token expiration during long offline sessions → implement proactive refresh 5 minutes before expiry

### Success Metrics
| Metric | Target | Measurement Method |
|--------|--------|-------------------|
| OAuth flow completion | 100% | User successfully connects Google account |
| Token refresh success | 99%+ | Successful API calls after token expiry |

### Alternatives Considered
#### Option B: Implicit Grant Flow
**Description:** Simpler flow without refresh tokens.
**Trade-offs:** Less secure, tokens exposed in URL fragment, not recommended for desktop apps.

#### Option C: Device Authorization Flow
**Description:** User authenticates on separate device.
**Trade-offs:** Better for input-constrained devices, but unnecessary friction for desktop users.
